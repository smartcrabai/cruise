# Plan verification models

Run `bash scripts/check_plan_verify_specs.sh` from the repository root. It uses the existing pinned setup, Quint 0.33.0, Apalache 0.62.1 and Alloy 6.2.0. Logs and receipts go into a fresh `target/formal-reports/plan-verify.*` directory. Setup or check failure is a failure, not a cached pass. The runner simulates 1,000 traces at seed 20261107, checks `safety` to eight transitions, and validates every Alloy command against its `expect` annotation.

The setup pins Node 26.12.1, Rust 1.99.1, Temurin JDK 25.0.5+8, and the Alloy distribution by SHA-256. Alloy 6.2.0 expresses expectations in the model using `expect 0` and `expect 1`, rather than an `--expect` CLI option. The runner selects every command explicitly and validates the fresh receipt. The Gherkin scenarios call the production extraction and verification functions with deterministic external-tool fixtures. They also cover the application-level two-turn Verify flow using a saved session and a deterministic backend fixture.

The Quint model abstracts one Verify claim, four sequential stages and a saved plan. It checks stage gating, failure precedence, plan immutability and that the Verify claim is held throughout its active stages. Competing Fix, Ask and Replan starts are abstract transitions sharing that claim. The model does not represent optional stages, process execution, cancellation, persistence failures or production code refinement. The Alloy model captures valid receipt SAT/UNSAT classification and includes a satisfiable witness. Invalid receipt structure and exit-code handling are outside its abstraction. Neither finite model establishes unbounded correctness or demonstrates that the Rust implementation refines the model.
